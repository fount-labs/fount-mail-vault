# The send keyset

Sending mail needs three long-lived keys the edge can't make each boot: an RSA-2048 DKIM key and
an Ed25519 DKIM key (RFC 8463 says to sign with both), and an Ed25519 key the gateway's relay
pins as the edge's client. They're the **send keyset**, kept apart from the keyset so the keyset
and its commitment never change.

| | Keyset | Send keyset |
|---|---|---|
| Holds | Address MAC key, routing data key, ACME account key | RSA DKIM key, Ed25519 DKIM key, relay client key |
| Encoding | `wire.Keyset.MarshalBinary` | `wire.SendKeyset.MarshalBinary`: version `1`, then each PKCS#8 DER key with a two-byte big-endian length, in that order |
| Commitment | `sha256("fount-mail-keyset/v1" ‖ keyset)`, `KEYSET_COMMITMENT` | `sha256("fount-mail-send-keyset/v1" ‖ send keyset)`, `SEND_KEYSET_COMMITMENT` |
| Generated by | `POST /generate`, in a release with no `KEYSET_COMMITMENT` | `POST /generate-send`, in a release with a `KEYSET_COMMITMENT` and no `SEND_KEYSET_COMMITMENT`, on a vault holding the keyset |
| Recovery shares | Yes | No. If both vaults die, make a new one (below) |
| If lost | Every mailbox ID changes | A new DKIM selector and relay pin. No mail is lost |

Both commitment vectors are in `wire`'s tests, each computed separately in Python.

## How it moves

It rides in the same sealed box as the keyset, as `send_keyset` in `wire.Payload`, on the same
`/transfer/begin` and `/transfer/finish` pull, with the same pins and minimum tags. There's no
new endpoint for it, no new key, and no new auth.

- **To a vault**, whenever the holder has one. A vault with a `SEND_KEYSET_COMMITMENT` takes only
  the matching send keyset, and a wrong one fails the whole pull, as a wrong keyset does. A
  vault with none takes the send keyset from a holder it has verified, as the first committed
  release took the keyset from the generator.
- **To an edge**, only once the vault's release has a `SEND_KEYSET_COMMITMENT`, because an edge
  doesn't verify the vault and has nothing else to check the keys against.
- **An edge or vault that predates it** calls `wire.Pull`, which never reads `send_keyset`. The
  field is also inside JSON, so an older `Payload` drops it. Edge v0.2.1 and vault v0.1.2 run
  unchanged against a vault that has one.

## Restarts

A vault keeps restoring until it holds everything its release commits to:

| Release | A restarted vault waits for |
|---|---|
| No `SEND_KEYSET_COMMITMENT` | The keyset. A send keyset comes along if the peer it pulls from has one |
| `SEND_KEYSET_COMMITMENT` set | The keyset and the matching send keyset |

With the commitment set, a vault that gets only the keyset from one peer, such as one that was
just restored from shares, keeps it, serves it, and asks every peer again for the send keyset,
backing off to two minutes. So when one vault has the send keyset and the other doesn't, the
one without it gets it from the other, whichever of them restarted. Until then it serves edges
the keyset with no send keyset, so a restarting edge can still receive mail.

If neither vault has it, nothing can make it again in that release: see "Losing it".

## Releases and owner steps

This mirrors the keyset's bootstrap. Suggested tags: `v0.2.0` is release N and `v0.2.1` is
release N+1. Both keep `KEYSET_COMMITMENT` as it is.

1. **Release N.** Merge, run *Build Image*, pin the digest, and release `v0.2.0` with
   `SEND_KEYSET_COMMITMENT: ""` and `/generate-send` in the shim paths, which `main` already has.
2. **Upgrade both vaults to N**, each with `--hold=true`. Each candidate pulls the keyset from
   production as usual. Wait for `has_keyset` on port 4443, then promote. Upgrading both keeps
   either able to restore from the other in this release. Edge v0.2.1 keeps pulling, and gets no
   send keyset from N.
3. **Generate once, on vault-a only:** `curl -X POST https://vault-a.../generate-send`. It answers
   with `send_commitment` and `send_public`. Check vault-a's `/status` shows the same
   `send_keyset_commitment`. There's no bundle to fetch. If it answers 409 "already holds a send
   keyset", someone called it first, which is harmless: read the commitment from `/status`.
   Don't call it on vault-b. A second send keyset there wouldn't be committed, and release N+1
   would refuse it.
4. **Release N+1.** Set `SEND_KEYSET_COMMITMENT` to that value, then Build Image, pin, and
   release `v0.2.1`. From then on every release keeps it, and none can generate.
5. **Upgrade vault-a to N+1** with `--hold=true`. The candidate pulls both from production
   vault-a. Wait for `has_send_keyset` and the right `send_keyset_commitment` on port 4443, then
   promote.
6. **Upgrade vault-b to N+1** the same way. Its own production instance has no send keyset, so
   the candidate gets it from vault-a. Wait for `has_send_keyset` before promoting.
7. **Publish the public halves** from `/status`'s `send_public`: `dkim_rsa_txt` at
   `f1._domainkey.fountbox.com`, `dkim_ed25519_txt` at `f1e._domainkey.fountbox.com`, and
   `relay_client_pin` on the relay (fount-infra).
8. **Release the edge** with the same `SEND_KEYSET_COMMITMENT`, only after both vaults run N+1.

Between steps 3 and 5, vault-a holds the only copy, so do them in one sitting. If vault-a
restarts in between, it pulls the keyset from vault-b, which has no send keyset, and the send
keyset is gone. Run step 3 again and use the new commitment. If N+1 was already released with
the old one, release N+1 again with the new one.

## Losing it

If no vault holds the committed send keyset, for example after a full recovery from shares,
the vaults hold and serve the keyset and keep asking each other for the send keyset. To make a
new one: release with `SEND_KEYSET_COMMITMENT: ""` again, repeat steps 2 to 8 with the next
selector number (`f2`, `f2e`), and keep the old DNS records for 30 days so signatures made
before still check.

## `/status`

| Field | Meaning |
|---|---|
| `has_send_keyset` | This vault holds a send keyset |
| `config_send_commitment` | `SEND_KEYSET_COMMITMENT`, empty in release N |
| `send_keyset_commitment` | The held send keyset's commitment |
| `send_source` | `generated`, or `pulled from <peer>` |
| `send_public` | `dkim_rsa_txt`, `dkim_ed25519_txt`, and `relay_client_pin`, the hex SHA-256 of the relay key's SubjectPublicKeyInfo |

## For the edge

```go
got, err := wire.PullKeysets(ctx, client, "https://"+host, transfer, attester, nil,
	wire.Commitments{Keyset: cfg.KeysetCommitment, Send: cfg.SendKeysetCommitment})
// got.SendKeyset is nil when that vault has none: try the next one.
rsaKey, err := got.SendKeyset.DKIMRSA()      // *rsa.PrivateKey, RSA-2048
edKey, err := got.SendKeyset.DKIMEd25519()   // ed25519.PrivateKey
relayKey, err := got.SendKeyset.RelayClient() // ed25519.PrivateKey
```

`wire.ValidateCommitment` checks `SEND_KEYSET_COMMITMENT` at boot. A send keyset that doesn't
match, or doesn't parse, fails the pull with an error naming the send commitment.
